04 · What is actually buildable

This is the part worth reading before writing code. I read the current Filen CLI source rather than the marketing page, and the situation changed recently.

The TypeScript CLI is sunset. FilenCloudDienste/filen-cli now tells you to stop using it; development moved to a Rust rewrite in filen-rs/filen-cli, currently public beta at v0.2.7. The Rust CLI dropped native sync, mount, webdav and s3 implementations — those now shell out to a managed rclone. Any plugin built today should target the Rust CLI and treat rclone as the transport for mounts/servers.

Sync pairs—Gone in the Rust CLI. rclone only.
Public links—Not in the Rust CLI yet (was in the TS one)
Notes / chats / contacts—SDK/API only — no CLI surface

Which gives an honest scope ladder:

  • v0.1 ship first — drive glyph + quota badge, browse with breadcrumb, stat details, download to ~/Downloads, upload via file picker, favorites, open web drive. Every one of these is a clean --json or exit-code call.
  • v0.2 next — transfers list with cancel, mounts & servers panel with toggles, trash view, notifications on completion.
  • later blocked upstream — search (needs a non-interactive flag), public links (needs CLI support), notes/chat (needs direct SDK use). Track these as upstream feature requests, not local hacks.
Design consequence: don't build a panel that promises sync pairs and public links today. Ship the browser — that's the thing you'd genuinely use daily, it's fully supported, and it's the part the website is slowest at.

05 · Security shape

The plugin runs unsandboxed inside omarchy-shell, and Filen is a zero-knowledge provider. Those two facts set hard rules.

  • Never touch the password. No password field in QML. Login happens in a terminal running the CLI's own prompt; the CLI stores the session in the system keyring.
  • Never read the auth config. filen-cli-auth-config.txt holds master keys, the private key and the API key in plaintext at mode 600. The plugin must not read, copy, or display it — it only checks that auth works, via filen whoami.
  • Never pass secrets in argv. Anything sensitive goes over stdin, the way the passpage plugin feeds curl a config file. Argv is world-readable in /proc.
  • No FILEN_CLI_PASSWORD. Environment variables leak to every child process. The keyring path is the only one.
  • Treat CLI output as hostile. Filenames are attacker-influenced (a shared folder can be named anything). Cap response size, parse JSON strictly, and pass paths as positional args — never interpolate into a shell string.
  • Servers bind to loopback by default, read-only, with generated credentials. A public bind is an explicit choice behind a warning.
  • No auto-install. The CLI's own auto-updater downloads and replaces binaries; the plugin must never trigger it silently. Copy the install command, let the user run it.
  • Confirm every destructive action. Delete and empty-trash go through ConfirmDialog defaulting to Cancel, exactly like passpage's delete flow.
Panel.qml→ Service.qml→ Process: filen --json→ keyring→ Filen API · secrets never cross the first two boxes

Traps already known (learned the hard way in your passpage plugin): KeyboardPanel doesn't scroll — wrap it in a Flickable. escape() is a reserved method name. h can't be a shortcut. qmllint can't parse qs.Ui imports, so the real gates are omarchy plugin validate . and qs log -p /usr/share/omarchy/shell --tail 60. Editing Panel.qml needs omarchy-restart-shell.
